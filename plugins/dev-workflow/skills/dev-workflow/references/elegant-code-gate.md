# 优雅代码门禁

## 判断顺序

### 1. 找到正确职责归属

列出：

- 数据归属。
- 状态归属。
- 生命周期归属。
- 交互归属。
- 降级归属。

修改应尽量落在能保证不变量的最上游职责归属。

### 2. 检查时序

如果 UI 需要二次通知才能正确展示，先问：

- 数据能否在创建 UI 前准备好？
- 列表刷新顺序能否调整？
- 真卡能否直接替换假卡？

不要依次升级为“业务事件 → 通用 sync → 新生命周期”，除非生产时序确实无法修正。

### 3. 缩小输入

组件需要的是语义，不一定是上下文。

例如组件只需 `showIndexInfo`，不要传完整 `StoryTab` 再让组件自行判断。渲染使用稳定快照，点击使用可靠的运行时状态。

### 4. 消除重复

检查是否出现：

- 两套相同状态计算。
- 新入口复制旧入口点击逻辑。
- 多个业务实现分别创建并覆盖同一配置。
- 新旧接口同时存在但无人清理。

优先修正公共职责归属，或让业务增量修改统一对象。

### 5. 控制复杂度

| 信号 | 默认处理 |
|---|---|
| 单一消费者的抽象 | 保持局部 |
| 为一个字段新增生命周期 | 回查时序 |
| 依赖字符串/尺寸推断场景 | 改为语义字段 |
| 为小修改改大量协议 conformer | 重新设计 |
| 只是替换现有尾部 accessory，却重建整个 View | 保留原安装链路，只增量替换尾部控件；同时逐项核对宿主标题色值、分隔线、间距与复用显隐，不把共享控件默认样式当成宿主样式。若设计明确是无分隔的独立强调按钮，按它自身规格展示 |
| 一个新交互态有独立按钮结构且被多个承载复用，却把它分别塞回各原 View | 抽成职责单一的独立状态 View，由各宿主只负责承载；转场可随该共享 View 复用 |
| 整体区域可点击且内部已有子 `UIControl`，却额外添加 tap 手势并用代理排除子控件 | 让整体 View 自身成为 `UIControl`，用 control event 承载整体点击；子控件依赖 UIKit 命中链独立响应 |
| View 生命周期内稳定的点击回调在每次 `setData/install` 时重绑，并在内容复位时清空 | 在 View/Component 初始化时绑定一次；点击读取可靠的当前业务状态，内容复位只重置展示。只有回调本身随数据模型变化时才重新绑定 |
| 图标+文案组合需要整体居中，却只设置 `UILabel.textAlignment` | 居中图标与 Label 的共同容器（如 Stack），因为 `textAlignment` 只控制 Label 边界内的文字。不同宿主布局语义不同时由宿主显式选择，不修改共享 View 默认值；图标本来就是固定边缘 accessory 时则仅居中文案 |
| 高风险改动无旧路径 | 增加 FF 降级 |
| `setData` 高频日志 | 改为状态变化日志 |

## 预检输出

小修改：

```text
Owner：...
最小方案：...
需避免：...
验证：...
```

复杂改动再补充数据流、时序、风险和替代方案。

## 红旗

- “先加个通知解决。”
- “默认值随便给一个就能编译。”
- “这里看起来像二级 Feed。”
- “复制原逻辑改一下最快。”
- “先把生命周期加到协议，以后可能有用。”
- “日志多打一点总没坏处。”

出现红旗时停止编码，重新确认职责归属、时序和最小接口面。

反例：新状态只改同一控件的文案或图标、没有独立交互结构和第二消费者时，留在原 View 内增量更新即可，不为形式统一额外拆 View。需要识别 tap 次数、与 pan/long press 协调或承载非控件手势语义时，仍使用手势识别器。若不同数据模型确实提供不同业务闭包，或组件没有可靠的当前状态入口，则允许数据绑定阶段替换回调，但复用边界必须完整清理。

# 文档内容纪律（需求理解 / 技术方案 / 任务拆分通用）

> 适用范围：`+需求理解.md`、`+spec.md`、`+task.md` 及通用模板生成的对应文档。
> 生成任何一份前置文档前，本文件与对应阶段 reference 都必须已读。
> Owner 逐字审阅的六项：目标行为与不覆盖边界 / 数据与接口依赖 / 验收标准 / 待确认与假设清单 / 方案取舍与影响面 / 任务拆分质量。

## A. 事实与待确认分离

- R1 正文只允许两种句子：有出处的断言，或标注"待确认 / 假设"的存疑项。
- R2 每条断言必须带出处（代码锚点 / 文档链接 / Owner 原话）。写不出出处 = 未证实，必须移入"待确认"表并标注"不同答案的影响"，禁止以结论口吻留在正文。
- R3 找不到代码位置、服务端字段或验收口径时：标阻塞 / 待确认，宁可留空，禁止编造填充。
- R13 更新既有文档前必须先读取当前文件内容、基于它增量修改；当前内容与历史 AI 写入不一致且非本会话所为时视为用户手改，以当前内容为准，禁止按记忆整篇重写或改回；只有发现逻辑冲突才列入待确认并向用户提问。

## B. 密度契约

- R4 禁止写入：需求原文与背景复述；空话套话；推理与推导过程；检索过程叙述；把检查清单当章节。
- R5 每个字段条目 ≤ 2 行：断言 + 出处。主流程用箭头链，每节点一行。
- R6 篇幅上限（不含待确认表）：需求理解 ≤ 60 行、技术方案 ≤ 80 行、任务拆分 ≤ 50 行。超限必须说明理由。
- R7 提交审批前执行"删废话自检"：删背景 / 过程 / 空话 → 无出处断言移入待确认 → 压到上限内 → 才标"待 Owner 审批"。

## C. 提问纪律

- R8 动笔前检索顺序：知识索引（`agent-memory/knowledge/知识索引.md`）命中专题 → 对应文档全文 → 工程 `doc/README` → 代码。检索范围含个人笔记库与播放知识库，不只代码库。
- R9 只允许问：会改变行为 / 方案 / 范围、且两库 + 代码都查不到答案的问题；问题必须附"已查过什么、为什么查不到"。
- R10 能从代码 / 两库确认的结论，禁止提问，直接写断言 + 出处。

## D. Owner 审阅视图

- R11 正文骨架 = Owner 六项审阅维度，其余内容不占正文空间。
- R12 骨架先行：正文展开前，先输出 ≤ 10 行骨架（六项各一行 + 主流程箭头链），Owner 确认方向后再补细节；确认前不生成完整文档。

## E. 提交前自检清单

1. 每条断言有出处吗？没有的进待确认了吗？
2. 有没有背景复述、空话、推理过程、检索过程？删了吗？
3. 超篇幅上限了吗？理由成立吗？
4. 提问的问题，两库 + 代码真查不到吗？附了查找记录吗？

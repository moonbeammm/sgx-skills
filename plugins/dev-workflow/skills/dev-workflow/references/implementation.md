# 代码实现

## 开始前

- 阅读目标模块知识库和相邻实现。
- 检查工作区，识别用户已有修改。
- 运行 `elegant-code-gate.md`。
- 明确验证目标和受影响的构建目标。
- 标准路径确认技术方案已批准且“实施前确认”已关闭；快速路径确认满足主工作流的快速路径条件。

## 实现纪律

- 每行改动都应直接服务需求。
- 优先沿用现有架构、命名和依赖。
- 通用配置由框架创建，业务只做增量修改。
- 不用 `spmid`、尺寸、视图层级等偶然特征推断业务语义。
- 不复制点击、状态同步、埋点或校验逻辑；复用真正的领域入口。
- 只依赖枚举自身的原始值合法化、默认值和下一态等纯规则，应由枚举同域的 initializer/convenience/inline function 承担；网络、存储或协调 API 不得为了复用而吸收这些类型规则。反例：转换需要实验、服务端配置或多个对象上下文时，留在拥有这些上下文的业务入口，不塞进枚举。
- 新旧状态由 FF 二选一时，各分支只写自己拥有的状态源和协议字段；不提供同时改新旧 Preference 的 `apply` 方法来维持双写一致。运行时需要旧布尔语义时，从当前分支的真值派生到 runtime config，不反写另一份 Preference。只有产品契约明确要求双写迁移时，才建立有生命周期和下线计划的迁移层。
- 上报基础类只提供公共参数注入和通用 click/exposure 能力；单一业务事件 ID、字段值域转换和上报时机留在具体业务入口。多个入口共享同一枚举字符串语义时，用作用域最窄的类型 extension/category 收敛纯转换，不向基础 tracker 增加业务方法；若转换依赖上下文或多个字段组合，则由业务上报入口组装，不塞进枚举。
- ObjC/Swift closure、delegate、Timer、KVO、Rx 订阅检查释放。
- UI 更新保证主线程，复用视图每次绑定都重置完整状态。
- 资源和国际化先搜索已有能力。
- 用户以“旧文案改为新文案”描述 Toast、标题或状态文案修正时，先全仓枚举旧资源标识和字面量的全部消费者，再按 Toast、可见标签、VoiceOver 状态等语义分类；替换所有与用户所指语义一致的消费者，不得以首个复现入口自行收窄范围。用户明确仅改某入口，或其它调用点语义确实不同时，保留局部修改。
- 公共请求参数审计所有独立入口。
- 同一资源支持 `aid`、`bvid` 等主标识与别名请求时，一致性校验必须按原请求实际携带的标识执行：主标识已提供则严格校验主标识，不能用别名相等掩盖主标识冲突；仅主标识缺失时才校验非空别名。服务端响应给出 canonical ID 后，后续异步任务、日志和回写竞态统一使用 canonical ID。若别名只用于展示、协议不接受别名请求，或协议明确要求多个标识同时一致，则按协议约束处理，不能套用回退校验。
- 实验接口客户端只负责请求、解析和保存原始实验数据；设备范围、组合条件和业务命中语义应收敛到工程统一的业务 FF 门面（例如 iOS `Memex.swift` 的 `FF`），业务消费者不得直接依赖实验客户端上的语义开关。业务契约要求单次 App 生命周期内实验值稳定时，FF 必须声明为不可变快照（例如 `static let`），不能用每次重新解释原始结果的 computed `var`。页面业务直接读取统一 FF；只有与业务来源解耦的播放器 service/widget 等能力层读取业务创建播放器时写入的 context/config FF，不在页面层经 service 或 delegate 再透传一层。实验接入只实现 Owner 明确的分流层级：若产品只要求 Release 读取 ABTest、Debug 使用本地二态覆盖，就用一个稳定语义值表达，不默认增加独立 DD 止损、来源枚举、raw group 或来源日志。只有产品明确要求独立紧急回滚或验收必须区分来源时，才增加对应止损层和诊断字段。反例：同一能力实例确实需要支持不同业务配置或运行时明确允许切换时，由 context/config 持有实例级值，不能强行改成全局快照。若工程没有统一 FF 门面或原始实验结果不可安全暴露，先确认既有架构再设计接入点，不自行复制一套门面。
- 需求只替换列表目标页或目标项判定时，目标确定后的动画、Focus、起播和生命周期沿用现有稳定链路。若某种手势解释会把原本可见的相邻目标扩成屏外目标，先向 Owner 确认“回弹起始项还是跨过起始项”，不得为未确认的屏外目标先移动取卡时机，再追加动画打断、陈旧回调或失败回滚。只有产品明确要求跨到屏外目标，或已有证据证明原生命周期链路存在缺陷时，才设计对应时序改动。
- 线上目标判定已经按输入状态分支（例如 `velocity > 0`、`< 0`、`== 0`）且需求只给各分支增加阈值时，优先在原分支条件内增量修改并复用原目标查找；不要先引入手势起点状态、方向一致性、目标枚举或独立状态机。只有新规则无法由原分支清晰表达、存在第二个真实消费者，或产品明确要求跨端共享同一独立算法时才抽象；即便抽象，也不得改变未要求的输入口径。
- 产品阈值表示“相对当前页的滑出距离或比例”时，不能直接使用整个列表的绝对 offset，也不能直接使用 `floor(offset / pageSize)` 基准页产生的原始进度。应先以当前页索引计算有符号相对偏移：其绝对值用于距离阈值及比例，符号只用于目标方向。必须覆盖非首页的小位移，以及正反方向相同距离的对称用例：否则绝对 offset 会让高页索引小位移误命中，原始进度则会把反向 `p` 计为 `1 - p`。反例：若产品定义的就是整个列表的绝对位置、基准页内位置，或只沿用系统 `0.5` 最近页判定，则保留对应原始值。
- 产品调整横竖手势归属时，先从真实视图层级定位能在子手势开始前稳定决定整条触摸链归属的最上游 owner，并用 `90°` 等极值配置验证它能否完整禁止下游横向行为。上游容器能够可靠拦截或拒绝本次手势时，只在该单一仲裁器门控，不因卡片内部还有 pan recognizer 就重复修改；只有下游 recognizer 不受上游仲裁、处于另一条触摸链，或实测仍能独立成功时，才在对应 owner 补同一语义门控。不能因为某个局部组件已有 velocity 就优先把规则放在那里。反例：父容器只观察方向但不拦截，或子 View 可通过独立窗口/手势依赖关系绕过父容器时，仍需分别处理真实的独立 owner。
- 实验值若只作为请求公参供服务端塑形响应，且响应协议已用字段有无、枚举或配置完整表达最终能力，则仅请求组装层读取统一 FF；响应后的模型、组件、状态机和埋点只消费真实协议，不重复用 FF 门控，否则会形成两个可能不一致的行为真值源。字段缺失就是回退路径，未知枚举按协议降级。反例：实验行为完全由客户端实现、服务端响应在实验组与对照组相同，或协议明确要求客户端结合 FF 解释同一字段时，业务入口仍应读取统一 FF。
- 响应已由服务端通过字段有无、判别值和字段组合完整塑形，且 Owner 明确服务端负责数据合法性时，客户端保留 `Int/String → enum` 这类单字段稳定语义的强类型映射，但不把映射失败或额外 `guard` 扩大为对正数 ID、非空字符串、固定 `goto/scene` 和跨对象组合的二次协议校验；后者会把服务端问题静默变成功能不展示。不要为了“相信服务端”退回散落的 magic number/string，也不要为强类型映射创建转抄协议字段的中间对象。仍必须保留可选值解包、URL 等本地解析、数组与索引边界、View 复用、线程和异步竞态安全；异常字段进入既有网络失败或降级链路后由服务端修复。反例：协议明确把值域降级交给客户端、输入来自用户或不可信本地存储，或非法值会导致崩溃和安全问题时，客户端必须增加对应校验。
- 协议按钮、卡片或入口对象已同时提供 `text/icon_url` 等展示字段和点击语义时，各布局 style 必须渲染同一个协议对象，style 只决定对齐、尺寸和组合方式；不能因为历史草案中某个 style 缺字段，就从相邻 `season/arc` 模型替换文案或图标。服务端未下发就按协议缺失处理，不在客户端拼另一套展示真值源。反例：协议明确规定不同 style 分别引用不同字段或对象时，按对应分支渲染。
- 判断旧实现是否仍在线、某修改是否属于 iPhone/iPad 等设备范围时，先从真实业务路由、控制器/Scene 装配和控件实例化反向确认活跃消费者；不能仅凭目录名、类名或“新旧代码”判断。若设备范围是该实验对所有消费者的固定产品契约，应收敛在统一实验门控内，消费者不重复拼设备条件；只有同一实验的消费者设备范围不同时，才在各业务配置入口追加判断。设备类型判断优先复用工程基础库统一能力（如 iOS `bfc_isIPad`），不重复底层 `userInterfaceIdiom` 判断。能力层保持设备和实验来源无关。仅修改明确单设备私有源码、且全仓无其它设备消费者时，不额外增加设备判断。
- 删除或修改公共类型、协议、头文件、服务注册类型时，先全仓枚举源码消费者和业务装配入口，再构建每个直接受影响的业务 target；不能只验证发起需求的模块。私有符号且全仓确认只有单一目标消费者时，仍按最小单目标验证。
- 共享协议模型通过 `type`、`goto` 等判别字段承载多个合法分支时，某一分支不再下发某字段不等于该字段可从共享模型删除；必须按每个判别值分别核对服务端契约与客户端消费者，只有所有合法分支都不再使用时才能删除。模型只对应单一分支，或各分支已经拆成独立强类型时，按各自真实契约收口即可。

## 按职责塑形数据，公共层只做通用编排

播放需求需要把 Router、业务配置或接口参数跨层传递时，先沿现有所有权链判断每层真正需要的数据，再决定类型和扩展点：

1. 不把完整上游对象塞进下游配置，只传递需求实际需要的语义。多个稳定且相关的字段跨层同行时，定义职责单一的小型配置类；不要为了省类型把 FlowConfig、Model 等长期边界退化成无语义字典。若所谓配置只是把互斥响应模型的原字段机械转抄一遍，消费者仍持有原协议对象，且各入口本就有明确所有者，则不建立统一 Configuration；让各入口直接消费自身协议。同步操作中，即使请求参数来自多个当前可用对象，只要唯一消费者会立即把这些值写入已有请求配置，就在消费入口直接组装，不为一次调用创建 Target；是否校验字段合法性遵循上游协议的明确职责约定。只有需要隔离下层协议依赖、跨异步生命周期冻结不可变快照，或多个消费者确实共享一组稳定同行语义时，才保留小型强类型配置。
2. 字典只用于字段集合本来就开放的协议载荷，例如业务预先构建的请求 `extra`。业务字段在上游组装，公共 Scene 只执行 `merge` 等通用流程，不识别 key、枚举业务值或回查 Router。
3. 数据沿既有 `FlowConfig → Model → Scene/业务实现` 主链传递。Scene 不额外保存来源 Router、重复状态或旁路属性；业务历史类型等语义在各业务原有配置点适配，不由公共 Scene 反向向业务取数。
4. 通用生命周期规则放在最接近数据所有权的类型或分类中，协调 Bloc 只调用结果。例如“同稿件继承”属于 FlowConfig，不属于 PlayerBloc。只有调用时已经能确定业务身份、并存在真实差异时才增加 Imp/协议扩展点，不能为假设中的定制提前设计分发层。
5. 优先维持单一数据源和现有行为入口。需求未明确要求用户操作失效、双向同步或额外生命周期时，不增加通知、版本号、监听多个 UI 入口或新的播放器服务接口。
6. 可读性优先于形式化封装：能用标准库 `merge`、已有模型映射或继承初始化直接表达，就不增加临时变量、包装方法、空转 override 或冗余 `init`。但不能通过压缩代码隐藏业务判断或生命周期边界。
7. 跨 Swift/ObjC 的公共配置在类型定义处保证互操作性；不要用 `@nonobjc` 绕开一个本应由 ObjC 消费的模型属性。仅 Swift 私有语义才保持非 ObjC 暴露。

决策检查：新增字段、对象、属性、通知、服务或协议方法前，必须回答“谁生产、谁拥有、谁消费、何时失效、为什么现有主链不能承载”。任一答案只是“以后可能定制”时，先不增加该抽象。

反例：下游确实需要完整 Router 语义、Scene 本身就是状态所有者，或多个已确认业务在身份可用的时机存在不同策略时，可以传完整对象、保存 Scene 状态或开放 Imp；此时要在方案中写明消费者、生命周期和差异证据，不能机械套用最小传递。

## 实现期方案同步


若变化会改变职责归属、接入点、公共状态或需求行为，停止扩大代码修改，返回技术方案或需求分析阶段。

## 验证

- `git diff --check`。
- iOS 需求默认不创建新的 XCTest 源文件或测试 target；优先使用静态检查、受影响 Bazel target 构建和明确人工路径。已有相关测试可按需运行，只有 Owner 明确要求时才新增 XCTest。
- Swift 可先运行 `xcrun swiftc -frontend -parse`，最终运行相关 Bazel 构建目标。
- Kotlin 修改先运行最小受影响范围的 ktlint，再运行相关 Bazel 构建目标。
- 区分本次错误与仓库已有 warning。
- 不在未验证时声称完成。
- 实施和基础验证完成后即标记“待 Owner 验收”；标准路径以 Owner 验收作为本地实现闭环完成条件。

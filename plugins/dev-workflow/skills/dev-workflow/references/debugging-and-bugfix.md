# 问题排查与 Bug 修复

## 证据链

按顺序证明：

1. 用户入口和复现条件。
2. 服务端或路由输入。
3. 模型解析和数据归属。
4. 状态写入与后续覆盖。
5. UI/播放器最终消费。

区分：

- 输入一开始就错。
- 输入正确，但后来被其他职责方覆盖。
- 数据正确，但 UI 复用或生命周期没有刷新。

## 日志策略

不确定根因时先加关键日志：

- 只覆盖关键状态迁移点。
- 带 `avid/cid/epid/tab/trigger/old/new` 等标识。
- 状态未变化时不重复打印。
- 问题确认后删除临时高频日志，保留少量长期诊断日志。

## 修复流程

1. 写出问题、根因和成功标准。
2. 运行优雅代码门禁。
3. 选择能修正职责归属或时序的最小方案。
4. 用 FF 保留旧路径，若改动影响播放关键链路。
5. 验证复现场景、相邻场景和开关关闭场景。
6. 清理临时事件、兼容路径、无用生命周期和日志。

Bug 记录只写：问题是什么、根因是什么、如何修复。

## Owner 验收 Bugs

Owner 在需求开发完成后创建 `<需求名>+bugs.md` 时：

1. 按文档顺序一次修复一条。
2. 保留 Owner 的问题原文。
3. 每修完一条，在该条下追加：

```text
原因：...
修复：...
```

4. 同步 `+task.md` 和原始需求入口进度区。
5. Bug 暴露需求、方案或任务遗漏时，主动更新 `+需求理解.md`、`+spec.md`、`+task.md`；实质改变边界时先请求 Owner 审批。
6. 全部修完后标记“待 Owner 复验”，不自行宣布验收通过。

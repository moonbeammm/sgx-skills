# 需求分析

> 遵守 `doc-content-discipline.md`：先骨架后细节；每条断言带出处；无出处一律进待确认。

## 目标

把需求还原成可验证的播放业务主流程，并尽早暴露待确认项。

Owner 提供原始需求 `.md` 时，必须按 `requirement-document-lifecycle.md` 在同目录创建或更新 `<需求名>+需求理解.md`，并等待 Owner 审批。没有原始需求入口时，标准路径使用 `/Users/sgx/Documents/Notes/4-Agents/sgx-dev-agent/template/播放模块需求分析.md`；快速路径不强制落文档。

## 输出顺序

1. **目标**：用户体验或业务指标为什么变化。
2. **范围**：Story、详情页、播放器、Resolver、Biz 组件及内容类型。
3. **主流程**：入口 → 数据 → 状态 → UI/播放器 → 埋点。
4. **变化点**：线上行为、新行为、实验组和对照组。
5. **待确认项**：阻塞项优先，逐个询问。
6. **验收标准**：正常、异常、降级和端差异。

## 平台与代码范围

区分：

- 产品目标平台。
- 实际修改的 KMP 源码集或旧平台目录。
- 公共代码会影响的平台。
- 对应 Bazel 或 Make 验证目标。

不能只用 `legacy-loktar` 或 `legacy-andruid` 判断整个 KNTR 任务的平台。

需求使用“详情页”“播放器”“Story”等框架级范围时，先从公共入口、Resolver/DI 注册和协议 conformer 枚举所有活跃业务实现，再决定接入范围；不能因为首个代码锚点位于 UGC、OGV 或 EDU 就把框架级契约收窄到该业务。只有需求明确写“仅某业务”，或路由与装配证据证明其他实现不会进入该框架时，才允许业务级收窄。反例：需求明确“仅 UGC 前台恢复”时，应落 UGC 业务库，不得扩到共享 Base。

## 专题检索记录

不要只读总入口 `README.md`。从需求提取中文词、英文词、业务别名、字段名、类名和函数名，检索相关规范（Spec）、文档和代码。

每个关键机制记录：

- 检索词和检索范围。
- 命中内容，或明确记录未命中。
- 1～3 个关键代码锚点。
- 每组锚点证明的需求范围、冲突或边界。

需求分析只保留锚点级证据，不展开完整调用链和文件级实施清单。

## 检查清单

- 服务端字段、枚举、优先级和接口范围是否完整。
- 是否存在 Shortcut、More、half-channel 等独立请求入口。
- 一级/二级 Feed、半屏/全屏、UGC/OGV/EDU/广告是否行为不同。
- 点击行为应对齐哪个现有入口。
- 数据是稳定快照还是运行时状态。
- FF、实验分组和对照组行为是否明确。
- 埋点、国际化、资源、无障碍和端对齐是否包含在验收中。
- 规范（Spec）检索记录和现有实现锚点是否足以支持结论。

## 待确认项写法

只问会改变方案或行为的问题。说明：

- 当前已知事实。
- 不同答案造成的实现差异。
- 推荐选择和理由。

不要把能从代码、接口或知识库确认的问题抛给用户。

只有新增材料、漏搜证据、待确认关闭或结论状态变化时更新需求理解文档；每次状态变化同步原始需求入口的 Agent 进度区。不要因为模板字段顺序或缺少空章节而返工。

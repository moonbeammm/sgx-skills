# 技术方案

> 遵守 `doc-content-discipline.md`：先骨架后细节；每条断言带出处；无出处一律进待确认。

## 先串主流程

先用一段流程描述数据如何进入系统、由谁持有、何时驱动 UI 或播放器。用户确认主流程后，再展开节点细节。

Owner 提供原始需求 `.md` 时，只能在 `+需求理解.md` 获批后按 `requirement-document-lifecycle.md` 创建同目录 `<需求名>+spec.md`。没有原始需求入口时，标准路径使用 `/Users/sgx/Documents/Notes/4-Agents/sgx-dev-agent/plugins/sgx-skills/template/播放模块技术方案.md`。方案状态必须是：草稿、待 Owner 审批、已审批、存在实施前确认或实现期更新。

## 方案结构

1. 背景、目标和非目标。
2. 当前链路与根因。
3. 目标链路与核心设计。
4. 数据模型、状态归属和接口变化。
5. 生命周期与线程时序。
6. UI、交互、播放器和埋点。
7. FF、降级、日志与监控。
8. 风险和验证。
9. 待确认项。

## 输入门禁

- 已有完成的需求分析或用户确认的稳定结论。
- 影响方案正确性的阻塞项已经关闭。
- 已记录专题规范（Spec）检索和关键代码锚点。
- 已明确目标平台、源码集和验证目标。

会改变职责归属、接入点、协议、状态策略、埋点口径或风险接受度的问题标记为“实施前确认”，未关闭前不得进入标准路径代码实施。

原始需求入口场景中，Spec 未获 Owner 审批前不得创建 Task；审批状态变化后同步入口进度区。

## 播放业务负责人检查

- 能否在数据源或公共职责归属解决，而不是消费端补偿。
- Story、详情页、小窗、共享播放器和播放器底层的边界是否清晰。
- 播放状态、页面状态、卡片状态和用户偏好是否混为一体。
- 新旧逻辑是否能通过 FF 独立切换。
- FF 默认值、关闭路径和清理时间是否明确。
- 是否影响秒开、预加载、首帧、播放切换、历史进度或心跳。
- 是否需要服务端、安卓、鸿蒙、数据或基础团队协作。

## 方案选择

至少比较：

- 最小补丁。
- 修正职责归属或时序的根因方案。
- 仅在确有长期复用价值时考虑抽象方案。

默认推荐根因方案，但不为单次需求建立无消费者的抽象。

## 实施步骤契约

按依赖顺序组织，不按文件列表堆叠。每步必须包含：

- 依赖前置。
- 需求或规范（Spec）依据。
- 代码位置。
- 改动目标。
- 不能影响的现有行为。
- 验证方式。

找不到关键代码位置时标记阻塞，不编造确定方案。自测、回归和兜底放在独立章节，不机械拆成实施步骤。

# 需求开发工作流

## 核心原则

站在负责人的角度对结果负责，而不只是完成局部代码修改。

先理解业务主流程、代码职责归属、数据流和生命周期，再选择最小且长期合理的方案。解决问题不等于方案优雅；能修正数据生产顺序时，不要用事件、补刷或新生命周期掩盖问题。

## 任务路由

只加载当前任务需要的 reference：

| 用户目标 | 必读 reference |
|---|---|
| 提供原始需求 `.md`、开发新需求、继续已有需求、Owner 审批、验收 Bugs | `references/requirement-document-lifecycle.md` |
| 分析需求、找待确认项 | `references/requirement-analysis.md` + `references/doc-content-discipline.md` |
| 编写或评审技术方案 | `references/technical-design.md` + `references/doc-content-discipline.md` |
| 拆分任务、制定执行顺序 | `references/task-planning.md` + `references/doc-content-discipline.md` |
| 编写或修改代码 | `references/implementation.md` + `references/elegant-code-gate.md` |
| 代码审查、代码优化 | 使用 `code-review` 技能；本地门禁 `references/elegant-code-gate.md` |
| 排查问题、修复 Bug | `references/debugging-and-bugfix.md` + `references/elegant-code-gate.md` |
| 交付总结、沉淀知识 | `references/knowledge-maintenance.md` |

复合任务按顺序加载，不要一次性加载全部 reference。

## 工作流

### 1. 需求阶段

- 串联端到端主流程，而不是先罗列文件。
- 明确业务目标、实验范围、端差异、服务端字段、交互职责归属和验收标准。
- 把未知项分为阻塞项与非阻塞项。
- 先检索 agent-memory 知识索引命中专题（领域地图 / 踩坑 / 协议 / 历史结论），命中即引用；能查到的禁止提问。
- 存在多种合理解释时先询问；明确且低风险的小修改直接执行。
- 生成需求理解 / 技术方案 / 任务拆分文档遵守 `references/doc-content-discipline.md`：动笔前先检索个人库命中专题，骨架先行，每条断言带出处，无出处的进待确认。
- 原始需求入口场景把结论写入 `+需求理解.md`，标记“待 Owner 审批”；审批前不得创建 Spec 或实施。
- 快速路径只保留必要事实和验收。

### 2. 方案阶段

- 定位数据归属、状态归属、交互归属和生命周期归属。
- 先设计旧路径、FF 止损、异常日志和验证方式。
- 优先修改正确的公共职责归属；不要在新入口复制一份近似逻辑。
- 对跨模块、播放器、列表和生命周期改动说明影响面。
- 原始需求入口场景把方案写入 `+spec.md`，标记“待 Owner 审批”；审批前不得创建 Task 或实施。
- 标准路径明确方案状态；存在实施前确认时不得进入代码实施。

### 3. 实现阶段

- 原始需求入口场景只有 `+task.md` 获 Owner 审批后才能开始实现。
- 执行优雅性门禁后再改代码。
- 改动必须可追溯到需求，保持最小文件和最小接口面。
- 复用现有模型、资源、国际化、埋点和行为入口。
- Kotlin 修改运行受影响范围 ktlint；Swift/ObjC 运行对应语法或 Bazel 验证。
- iOS 需求开发默认不新增 XCTest 源文件或测试 target，也不把新增 XCTest 作为完成条件；只有 Owner 明确要求时才编写。通用 TDD 或测试技能不得自行扩大该边界。
- 验证默认止于受影响单模块：执行必要的静态检查、已有且相关的检查以及单模块 Bazel 构建。不得把粉版、HD 或其他 App 整包构建作为需求开发的默认验证，也不得以“更全面”为由自行扩大验证范围；只有 Owner 明确要求时才执行整包验证。
- 未经用户明确要求，不提交、不推送、不修改合并请求状态。
- 开发过程中持续更新 `+task.md` 的任务状态、实际改动和验证结果。
- 标准路径发现实现期约束或方案偏差时同步更新 `+需求理解.md`、`+spec.md`、`+task.md`；实质改变产品行为、范围、协议或公共职责时回到 Owner 审批。

### 4. 审查阶段

- 先核对需求和方案，再检查正确性、内存、时序、止损、日志和坏味道。
- 审查当前分支时只审本分支引入的变化，区分仓库基线问题。
- 发现“可以工作但职责不对”的实现时，指出更合适的职责归属和收敛方式。
- 普通分支或合并请求质量审查使用 `code-review` 技能与本地代码审查引用。

### 5. 排障阶段

- 不猜根因。先确认输入是否正确，再找后续覆盖者。
- 优先用代码链路、日志、接口数据和状态变化证明结论。
- 日志记录状态变化和关键标识，避免高频无差别打印。
- 修复根因后检查能否删除临时事件、补刷、兼容代码和排障日志。

### 6. 交付与沉淀

- 汇报结果、验证、风险、未完成项和是否提交。
- 原始需求入口场景在 `+task.md` 标记“待 Owner 验收”，并同步入口索引；本地完成不等于验收通过。
- Owner 创建 `+bugs.md` 后按顺序一次修复一条，每条下面只追加“原因”和“修复”，必要时主动同步前三份文档。
- 主智能体在最终验证开始时把实际使用清单交给记录子智能体，并继续执行最终验证；
- 标准路径本地实现完成并完成基础验证后即标记“待 Owner 验收”，以 Owner 验收作为本地实现闭环完成条件；快速路径完成简短一致性检查即可。
- 判断是否需要更新个人笔记或工程播放知识库。
- 检查用户修正、最终合并请求差异、重复问题或验证证据是否暴露了智能体的长期缺口；有可复用认知时写入 agent-memory 或列入 `4-Agents/plugins/sgx-skills/待确认清单.md` 由 Owner 确认，不自行修改规则；没有新增认知时不产生沉淀。
- 稳定、通用且经代码验证的知识同步到对应工程 `doc/`；一次性需求细节留在个人笔记。
- 更新工程正文时同步维护对应 `README.md` 文档地图。

## 强制质量门禁

代码编写、缺陷修复方案、代码审查和代码优化前，必须回答：

1. 真正的问题、数据源和职责归属是什么？
2. 能否通过修正生产时序或公共职责归属解决？
3. 下层需要完整上下文，还是一个稳定的语义值？
4. 是否新增了重复状态、事件、生命周期或复制逻辑？
5. 关闭开关后能否完整回到旧路径？
6. 内存、线程、复用、异步回调和订阅释放是否安全？
7. 日志是否足够定位且不会高频污染？
8. 有没有更小、更符合现有架构的方案？

小修改用几行完成门禁，不输出长篇设计；跨协议、框架或生命周期改动必须展开说明。

## 停止条件

出现以下情况时暂停实现并向用户确认：

- 需求理解、Spec 或 Task 尚未获得对应 Owner 审批。
- 服务端字段、交互含义或验收标准存在冲突。
- 多种方案会造成明显不同的产品行为。
- 修复需要跨职责归属修改或扩大到用户未授权的模块。
- 无法确定旧路径、降级方式或数据来源。

不要因问题困难而停止；先穷尽安全的代码、文档、日志和历史实现检查。

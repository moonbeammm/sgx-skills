# 任务拆分

> 遵守 `doc-content-discipline.md`：每条断言带出处；无出处一律进待确认；篇幅 ≤ 50 行。

## 文档门禁

Owner 提供原始需求 `.md` 时，只能在 Spec 获批后创建同目录 `<需求名>+task.md`。Task 获 Owner 审批和开发授权前不得修改生产代码。

## 原则

按可独立验证的能力拆分，不按文件数量拆分。

## 顺序

1. 数据协议、实验和公共入口。
2. 职责归属与状态流。
3. UI/播放器消费者。
4. 埋点、国际化和资源。
5. 日志、降级和清理。
6. 编译、测试和验收。
7. 文档更新。

## 每个任务必须包含

- 目标和明确边界。
- 主要代码位置。
- 上游依赖。
- 需求或规范（Spec）依据。
- 不能影响的现有行为。
- 完成标准。
- 验证命令或验收路径。
- 风险与 FF。

避免把“开发功能”作为一个大任务，也避免把每个文件拆成机械任务。

## 开发期更新

- 开始任务前标记“进行中”。
- 完成后记录实际改动、验证结果、方案偏差和剩余项，再标记“已完成”。
- 阻塞时写清阻塞证据和需要的 Owner 决策。
- 每次状态变化同步原始需求入口的 Agent 进度区。
- 全部本地实现和验证完成后，Task 总状态标记为“待 Owner 验收”，不得自行标记需求验收通过。

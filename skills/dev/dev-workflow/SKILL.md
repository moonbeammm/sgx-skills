# 需求开发工作流

## 核心原则

站在负责人的角度对结果负责，而不只是完成局部代码修改。

## 执行熔断（必须）

- 开始回复先列出目标、允许修改路径、明确不做项、完成条件和本阶段预算。默认预算为 20 分钟或 10 次工具调用，先到者触发；预计超出时先停下来分阶段说明。
- 只修改已列入白名单的路径。需要扩大范围、删除/迁移文件、改自动任务或调用外部系统时，先停并取得用户确认。
- 每 5 次工具调用或 10 分钟发送一次进度；预算耗尽立即停止并报告，不静默续跑。
- 网络、依赖或模型接口失败最多重试 1 次；仍失败就标记“未验证”，交付已有本地结果，不继续等待。
- 后台子 agent 最多 1 个，最长等待 5 分钟；主 agent 不等待其完成，也不允许递归派发。
- 达到完成条件后立即交付；历史回填、全量扫描、整包构建和端到端模型测试不自动追加。
- 最终报告必须分别列出已修改、未修改、已验证、未验证和下一步；“未验证”不得写成“完成”。

开始任务前先读取 `/Users/sgx/Documents/Notes/4-Agents/memory/BOOTSTRAP.md`，按任务关键词和 `project:bilibili-client` 调用 `/Users/sgx/Documents/Notes/4-Agents/memory/tools/lookup`，并在第一条回复回执检索状态。命中事实必须标注 ID、库内位置和来源；未命中、冲突或读取失败按启动协议处理。

每次任务还必须读取同目录的 `../session-recording.md`（canonical：`/Users/sgx/Documents/Notes/4-Agents/plugins/sgx-skills/skills/dev/session-recording.md`）：目标明确后确定唯一主文档和 `task_id`，按协议创建/复用根目录会话记录，并尽力启动后台 recorder；快速路径同样执行。会话期间只维护时效性快照，不直接写长期事实账本。

先理解业务主流程、代码职责归属、数据流和生命周期，再选择最小且长期合理的方案。解决问题不等于方案优雅；能修正数据生产顺序时，不要用事件、补刷或新生命周期掩盖问题。

## 会话记录硬门槛

1. 目标明确前不创建日志；目标明确后先按 `session-recording.md` 复用/原子创建唯一主文档，再开始实质工作。用户明确给出的原始 `.md` 优先，不能仅凭相似文件名猜文档。
2. 确定 `task_id` 后立即尽力派发一个后台 recorder，发送主文档路径、协议和精简增量；主 agent 不等待它完成，继续回答并在关键状态变化时发送 checkpoint。
3. 主 agent 维护需求生命周期的 `AGENT_PROGRESS` 和 `+需求理解/+spec/+task/+bugs`；recorder 只维护 `AI_SESSION_RECORD`。会话期间双方都不得写 `facts.jsonl`、`pending.jsonl`、`events.jsonl`。
4. 每次更新先重读并保护用户正文；最终回复前按协议有界等待 recorder，必要时在确认租约结束后回退，并在正常交付结果后附记录报告。不得把失败写成成功。

## 工作流

### 1. 需求阶段

- 串联端到端主流程，而不是先罗列文件。
- 明确业务目标、实验范围、端差异、服务端字段、交互职责归属和验收标准。
- 把未知项分为阻塞项与非阻塞项。
- 先按 `../session-recording.md` 确定主文档、`task_id` 和 recorder，再开始实质分析；主文档已有时不得另建平行会话日志。
- 先检索 memory 正式事实账本，命中即引用；能查到的禁止重复提问。
- 存在多种合理解释时先询问；明确且低风险的小修改直接执行。
- 生成需求理解 / 技术方案 / 任务拆分文档遵守 `references/doc-content-discipline.md`：动笔前先检索个人库命中专题，骨架先行，每条断言带出处，无出处的进待确认。
- 原始需求入口场景把结论写入 `+需求理解.md`，标记“待 Owner 审批”；审批前不得创建 Spec 或实施。
- 快速路径只保留必要事实和验收。

### 2. 方案阶段

- 定位数据归属、状态归属、交互归属和生命周期归属。
- 先设计旧路径、FF 止损、异常日志和验证方式。
- 优先修改正确的公共职责归属；不要在新入口复制一份近似逻辑。
- 对跨模块、播放器、列表和生命周期改动说明影响面。
- 原始需求入口场景把方案写入 `+spec.md`，标记“待 Owner 审批”；审批前不得创建 Task 或实施。
- 标准路径明确方案状态；存在实施前确认时不得进入代码实施。

### 3. 实现阶段

- 原始需求入口场景只有 `+task.md` 获 Owner 审批后才能开始实现。
- 执行优雅性门禁后再改代码。
- 改动必须可追溯到需求，保持最小文件和最小接口面。
- 复用现有模型、资源、国际化、埋点和行为入口。
- Kotlin 修改运行受影响范围 ktlint；Swift/ObjC 运行对应语法或 Bazel 验证。
- iOS 需求开发默认不新增 XCTest 源文件或测试 target，也不把新增 XCTest 作为完成条件；只有 Owner 明确要求时才编写。通用 TDD 或测试技能不得自行扩大该边界。
- 验证默认止于受影响单模块：执行必要的静态检查、已有且相关的检查以及单模块 Bazel 构建。不得把粉版、HD 或其他 App 整包构建作为需求开发的默认验证，也不得以“更全面”为由自行扩大验证范围；只有 Owner 明确要求时才执行整包验证。
- 未经用户明确要求，不提交、不推送、不修改合并请求状态。
- 开发过程中持续更新 `+task.md` 的任务状态、实际改动和验证结果。
- 标准路径发现实现期约束或方案偏差时同步更新 `+需求理解.md`、`+spec.md`、`+task.md`；实质改变产品行为、范围、协议或公共职责时回到 Owner 审批。

### 4. 审查阶段

- 先核对需求和方案，再检查正确性、内存、时序、止损、日志和坏味道。
- 审查当前分支时只审本分支引入的变化，区分仓库基线问题。
- 发现“可以工作但职责不对”的实现时，指出更合适的职责归属和收敛方式。
- 普通分支或合并请求质量审查使用 `code-review` 技能与本地代码审查引用。

### 5. 排障阶段

- 不猜根因。先确认输入是否正确，再找后续覆盖者。
- 优先用代码链路、日志、接口数据和状态变化证明结论。
- 日志记录状态变化和关键标识，避免高频无差别打印。
- 修复根因后检查能否删除临时事件、补刷、兼容代码和排障日志。

### 6. 交付与沉淀

- 汇报结果、验证、风险、未完成项和是否提交。
- 原始需求入口场景在 `+task.md` 标记“待 Owner 验收”，并同步入口索引；本地完成不等于验收通过。
- Owner 创建 `+bugs.md` 后按顺序一次修复一条，每条下面只追加“原因”和“修复”，必要时主动同步前三份文档。
- 主 agent 在关键结论/状态变化时向 recorder 发送精简快照；最终验证前发送实际使用清单，最终回复前按协议做一次有界等待并报告记录状态。
- 标准路径本地实现完成并完成基础验证后即标记“待 Owner 验收”，以 Owner 验收作为本地实现闭环完成条件；快速路径完成简短一致性检查即可。
- 会话期间不直接更新 `facts.jsonl`、`pending.jsonl` 或 `events.jsonl`；只在会话快照中保留可追溯的结论和来源。由每日 08:00 任务按 `session-recording.md` 提炼事实、写账本并回填引用。
- 记录区只保留精简续接快照，不新增事实候选章节；每日任务成功入账后才更新主文档的 `AI_KB_LINKS` 引用区。
- 稳定、通用且经代码验证的知识同步到对应工程 `doc/`；一次性需求细节留在个人笔记。
- 更新工程正文时同步维护对应 `README.md` 文档地图。

## 强制质量门禁

代码编写、缺陷修复方案、代码审查和代码优化前，必须回答：

1. 真正的问题、数据源和职责归属是什么？
2. 能否通过修正生产时序或公共职责归属解决？
3. 下层需要完整上下文，还是一个稳定的语义值？
4. 是否新增了重复状态、事件、生命周期或复制逻辑？
5. 关闭开关后能否完整回到旧路径？
6. 内存、线程、复用、异步回调和订阅释放是否安全？
7. 日志是否足够定位且不会高频污染？
8. 有没有更小、更符合现有架构的方案？

小修改用几行完成门禁，不输出长篇设计；跨协议、框架或生命周期改动必须展开说明。

## 停止条件

出现以下情况时暂停实现并向用户确认：

- 需求理解、Spec 或 Task 尚未获得对应 Owner 审批。
- 服务端字段、交互含义或验收标准存在冲突。
- 多种方案会造成明显不同的产品行为。
- 修复需要跨职责归属修改或扩大到用户未授权的模块。
- 无法确定旧路径、降级方式或数据来源。

不要因问题困难而停止；先穷尽安全的代码、文档、日志和历史实现检查。

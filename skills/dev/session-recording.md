# 会话记录协议

`dev-workflow` 与 `bugfix-workflow` 共用本协议。根目录会话文档是正在进行任务的精简、时效性续接快照；长期事实仍由每日 08:00 任务从原始会话和材料提炼到 `/Users/sgx/Documents/Notes/4-Agents/memory`。会话期间不把快照当事实库。

## 1. 主文档与稳定身份

每次进入任一工作流，先读取本协议；目标明确后再开始实质分析，并确定唯一 `task_id` 和主文档。

### 选择顺序

1. 用户在当前会话明确给出路径、附件或已打开的原始需求/问题 `.md`。只有这种“明确提供”才算原始文档；用户只粘贴文本、或目录中恰有相似文件，不能据此猜文件。路径在 Notes 内时可原地维护；路径在 Notes 外时默认只读，在 Notes 根目录创建受管续接文档并链接原文，只有用户明确授权原地写入才例外。
2. 当前会话已经使用、且标记中的 `task_id` 与本任务匹配的受管文档。
3. Notes 根目录中按目标和上下文唯一匹配的受管文档。存在多个候选时先列出候选并询问，不覆盖、不合并猜测。
4. 没有主文档且目标已经明确时，在 Notes 根目录创建新文档。目标未明确时先澄清，不创建占位日志。

原始需求入口仍遵循 `references/requirement-document-lifecycle.md`：Notes 内原始需求文件是阶段性任务的总入口，衍生的 `+需求理解.md`、`+spec.md`、`+task.md`、`+bugs.md` 只作为关联工件，不另建平行会话日志。Notes 外原始文档默认是只读输入，Notes 根目录新建的受管续接文档才是记录主文档，只有用户明确授权才可原地维护外部原文。没有原始入口的快速开发或排障任务使用根目录会话文档作为主文档。

首次建档生成 UUID（例如 v4）作为 `task_id`。它不随改名、跨日期或用户移动而变化；用户负责任务完成后的迁移，AI 不搬回、不复制。拿到移动后的路径或 `task_id` 后继续原记录。

### 新文件名与并发占名

文件名为 `MMDD-事件或问题或目标.md`，日期取 `Asia/Shanghai`；一级标题为 `# MMDD-事件或问题或目标`。目标只做精简表述；过长时在安全长度内截断文件名，完整目标保留在 `目标` 字段。清理 `/\\:*?"<>|`、换行和首尾空白，但不改变任务含义。

创建必须使用原子独占方式（`O_EXCL` 或等价的临时锁/重命名），创建后立即重读并校验 `task_id`。目标文件已存在时先读取：只有 marker 明确含同一 `task_id` 才复用；无 marker、归属不明或含其他 `task_id` 一律不得覆盖，依次尝试 `-2`、`-3`（继续碰撞再递增）。竞争结果无法确认归属时报告 `recording=conflict`，不覆盖任何文件。

## 2. 结构、保护区与写者边界

五类区域中，三类机器区必须是独立、成对、唯一的顶层 marker，禁止嵌套、重复或把一个区域包进另一个区域：

| 区域 | 唯一写者 | 范围 |
| --- | --- | --- |
| 用户保护区（`背景`、`诉求`） | 用户 | AI 不改、不重排、不删除 |
| 工作流正文（`需求理解`、`spec`、`task`、`bugs` 等） | 主 agent | 按工作流增量维护；用户手改优先 |
| `AGENT_PROGRESS` | 主 agent | 仅按需求生命周期更新；recorder/日更不改 |
| `AI_SESSION_RECORD` | recorder；失败回退时由主 agent 接管 | 只写会话续接快照 |
| `AI_KB_LINKS` | 每日任务 | 只写已成功入账事实的引用和回填状态 |

机器区采用以下固定骨架。字段没有内容时写 `暂无` 或 `不可得（原因）`，不能留给新 agent 猜测：

```html
<!-- AI_SESSION_RECORD_START schema=1 task_id=<uuid> revision=<n> ai_sha256=<hash> -->
## 会话续接
- 目标：
- 范围/不在范围：
- 当前状态：
- 已完成与证据：
- 已确认决定：
- 阻塞/待确认：
- 下一步：
- 关联工件：
- as-of（Asia/Shanghai）：
- 会话定位：
- 更新时间（Asia/Shanghai）：暂无
- 记录状态：pending
<!-- AI_SESSION_RECORD_END -->

<!-- AI_KB_LINKS_START schema=1 -->
## 知识库引用
- 已回填事实：暂无
- 最近回填窗口：暂无
- 回填状态：待每日提炼
- 更新时间（Asia/Shanghai）：暂无
<!-- AI_KB_LINKS_END -->
```

`revision` 从 1 开始递增；`ai_sha256` 是上次写入的 `AI_SESSION_RECORD` 区正文（不含 start/end marker 属性）的 SHA-256，用于发现用户或并发改动。哈希无法计算时写 `不可得`，但仍须重读和报告。`记录状态` 只使用 `pending|spawned|completed|fallback|failed|deferred|conflict`。

保护规则：

- `背景`、`诉求`标题（可带括号说明，允许 Markdown 的任意标题级别）从该标题起到下一个同级或更高级标题前是用户保护区，按字节保留文字、顺序和格式。存在标题就锁定；缺少标题不阻塞建档，不自行补写，最终报告说明缺失。标题重复、层级或边界无法判断、marker 重复/损坏时暂停写入并报告冲突。
- 已有 `AGENT_PROGRESS` 时保持其完整 marker 和相对位置；AI 两区作为独立顶层区追加在文件末尾（不得插入其 marker 内）。没有 `AGENT_PROGRESS` 时不擅自创建，除非需求生命周期明确要求。
- 主 agent 可以按各自工作流更新 `AGENT_PROGRESS`、需求理解/spec/task/bugs 等工件；recorder 只能写 `AI_SESSION_RECORD`，日更只能写 `AI_KB_LINKS`。任何角色都不能把完整 transcript 粘进机器区。
- `关联工件` 只填写已经存在且实际使用的路径；原始需求同目录衍生文档使用相对原始文档目录的真实链接，根目录任务可用从 Notes 根目录起的相对路径或绝对路径。不存在时写 `未创建`，不猜文件名或路径。

## 3. 会话续接快照

快照只写当前会话需要的精简信息：目标、范围、状态、已完成事项及证据（宿主提供 locator 时一并记录，否则写不可得）、已确认决定、阻塞/待确认、下一步、真实工件链接和时间定位。它不是 transcript，也不是“事实候选/待日更提炼”清单；不复制完整聊天，不把推测写成结论。没有可定位证据的内容不能在日更中升级为事实。

在以下时点刷新：身份确定后、目标/结论/状态/验证发生变化时、最终回复前各一次；无变化不重复追加。`as-of` 使用 `Asia/Shanghai`。`会话定位` 只使用宿主实际提供的 thread/task ID、turn 或 message ID；不可得时明确写 `不可得（宿主未提供）`，绝不编造 ID。

每次写入前重新读取文件，校验三类机器 marker、保护区、`task_id`、revision/hash 和用户当前内容；recorder/日更只替换自己拥有的区域，主 agent 只增量维护明确的工作流正文。写入者须保留本次读取的 baseline 正文，发现 hash 不一致时才可基于 baseline/current/new 做字段级三方合并并优先保留用户修改；没有 baseline 或无法安全合并则原文保留并报告 `recording=conflict`。优先写临时文件后原子替换，禁止半写文件。

## 4. 后台 recorder 与回退

主 agent 确定主文档和 `task_id` 后，尽力启动一个后台 recorder，然后立即继续主任务，不等待 recorder 首次写入。同一会话只启动一个 recorder，并向它发送精简增量（目标、状态、决定、证据、下一步和真实路径），不发送或要求它暴露内部推理。

同一会话只派发一个 recorder 即取得该 `task_id` 的逻辑写者租约；宿主提供协调/锁机制时优先使用，没有锁时以“单 recorder + 写前重读/原子替换”保证独占。检测到另一写者或无法确认文件归属时不得抢写，按 `deferred` 或 `conflict` 报告。recorder 是 `AI_SESSION_RECORD` 的唯一正常写者，只能更新该区及其区内更新时间；不得再次调用 dev/bugfix workflow，也不得递归派发子 agent。它不得写 `facts.jsonl`、`pending.jsonl`、`events.jsonl`，不得改 `背景`/`诉求`、`AGENT_PROGRESS`、其他任务文档、代码、插件或 Git。

最终回复前主 agent 做一次有界等待并取得 recorder 的终态：

- `completed`：recorder 已写入并校验，主 agent 不再并行写该区。
- `failed`：明确写入/权限错误；主 agent 在重新读取并确认租约结束后尝试最小快照回退，回退也失败则保留原文并报告原因。
- `fallback`：recorder 不可用或已确认失败，主 agent 接管租约并只写最小快照。
- `deferred`：超时但无法确认 recorder 已结束；不得抢写，报告下次继续。
- `conflict`：用户/并发修改无法安全合并；不覆盖，报告冲突。

回退前必须确认 recorder 已终止或明确放弃租约，避免双写覆盖。宿主不支持后台 agent、目录不可写或原子替换失败时，主任务继续，最终如实报告 `failed`/`fallback`/`deferred`/`conflict`，不得伪造 `completed`。

## 5. 每日事实提炼与引用回填

每日 08:00 任务扫描目标日窗口（默认运行日前一自然日，含该窗口内的进行中任务）和 Notes 下可读材料。`AI_SESSION_RECORD`、`AI_KB_LINKS` 只用于定位任务，不能作为新事实来源。事实必须追溯到原始用户消息、工具消息，或有定位的文件/代码/日志/构建证据；用户确认或可复现观察才可进入 `facts.jsonl`。会话来源拿不到宿主要求的 message ID 时，写入 `pending.jsonl` 或报告来源不可定位，绝不以 AI 快照替代来源。推断、冲突、来源不全或仅来自 AI 归纳的内容进入 `pending.jsonl`，不写成事实。

先校验并幂等写入 `facts.jsonl`/`pending.jsonl`/`events.jsonl`，确认账本成功后才在每个相关受管主文档各自的 `AI_KB_LINKS` 区增加 `F-*`、`facts.jsonl#F-*` 和原始来源定位；同一事实可被多个文档引用，逐文档去重，语义上已存在的事实复用原 `F-*`，无法判定重复时写 `pending` 而不是新增正式事实，不能重复写账本。引用格式精简、路径真实；不得把 AI 快照当 source。日更只可修改 `AI_KB_LINKS` 区及该区更新时间，不改 `背景`、`诉求`、`AGENT_PROGRESS`、`AI_SESSION_RECORD` 或其他正文；用户手改优先。

账本成功而回填失败时保留账本、报告失败并保留可重试状态；不推进错误游标，下一次重试且不重复事实/引用。任一来源、校验、报告或回填失败都要在日更报告中列出，不能宣称完整覆盖。自动任务不执行任何 Git，Obsidian Git 的 commit/push 独立运行。

## 6. 交付检查与报告

最终回复必须先给正常的开发/排障结果，再附精简“记录报告”，至少包含：主文档是 `created` 还是 `reused`、绝对路径、稳定 `task_id`、最后 checkpoint 时间、本轮实际更新的 AI 区/工件/引用、未修改的保护区、recorder 状态（上述枚举之一）以及失败/冲突/未验证边界。不要展示 recorder 内部推理。若任务没有新增长期事实，也要说明“本会话未直接写事实库，等待每日提炼”。
